# MARMOO Reviews CRM — поточний стан і правила роботи

Це головний технічний опис модуля `dashboard_reviews`. Читайте його перед будь-якими змінами у відгуках. Файл `REVIEWS_CRM_ROLLOUT.md` зберігає історію початкового виправлення та запуску; актуальна поведінка описана тут.

## Призначення

Модуль є єдиним робочим інтерфейсом менеджера для ручного ведення відгуків із Google Maps, Instagram, ChoiceQR, Glovo, Bolt Food та інших джерел. Менеджеру не потрібен доступ до Google Sheet або Google Apps Script.

Продакшн CRM доступна через route `?view=dashboard_reviews` на GitHub Pages цього репозиторію. Чинний Reviews API endpoint налаштований як `MARMOO_REVIEWS_API_URL` у `.github/workflows/deploy.yml`. ID таблиці й назва аркуша визначені у `google-apps-script/reviews-api.gs`. Не дублюйте ці значення в нових документах; перед зміною production deployment звіряйте їх із власником.

## Архітектура

```text
Менеджер
  → React UI: src/ReviewManagementDashboard.tsx
  → API client: src/reviewsApi.ts
  → Google Apps Script web app v2
  → Google Sheet / Reviews
```

Основні файли:

- `src/ReviewManagementDashboard.tsx` — інтерфейс, стани синхронізації, пошук, фільтри, створення, редагування та видалення.
- `src/reviewsApi.ts` — типи, HTTP-запити, таймаут і перевірка відповідей API.
- `src/index.css` — стилі форм і контраст системних випадаючих списків.
- `google-apps-script/reviews-api.gs` — точна копія серверного коду Apps Script v2.
- `scripts/test-reviews-api.mjs` — контрактні тести бекенду на mock Google Sheet.
- `scripts/test-reviews-ui.mjs` — браузерні CRUD-тести на desktop і mobile.
- `.github/workflows/ci-work-branch.yml` — перевірка pull request.
- `.github/workflows/deploy.yml` — перевірка API, production build і публікація `gh-pages` після push у `main`.

## Що бачить і може робити менеджер

- Переглядати лічильники: усього, середня оцінка, без відповіді, критичні та відсоток опрацьованих.
- Шукати за автором, текстом відгуку та текстом відповіді.
- Фільтрувати за статусом, оцінкою та джерелом.
- Сортувати за датою або показувати критичні відгуки першими.
- Додавати відгук вручну.
- Редагувати джерело, дату, автора, оцінку, текст і URL.
- Змінювати статус, публічну відповідь, внутрішній коментар і відповідального.
- Очищати помилкову відповідь. Якщо очищена відповідь мала статус `sent`, статус стає `needs_reply`.
- Копіювати відповідь для ручної публікації у вихідному сервісі.
- Швидко закривати або повертати відгук у роботу.
- Фізично видаляти запис після системного підтвердження.

Важливі UX-рішення:

- `Імпорт CSV` прибраний з інтерфейсу менеджера. API все ще підтримує `bulkUpsert` для технічного обслуговування, але звичайний користувацький сценарій — ручне додавання через форму.
- Окремий фільтр за відповідальним прибраний. Поле `assignee` залишене всередині редактора як необов’язкове на випадок роботи кількох менеджерів.
- Відповідь зберігається в CRM, але не публікується автоматично у Google, Instagram або іншому джерелі. Менеджер копіює та публікує її вручну.
- Нативні `<select>` мають клас `review-select`, `color-scheme: dark` і явні кольори `<option>`. Не прибирайте це: без нього Windows/Chrome може показати білий текст на світлому системному меню.

## Модель даних

Основний тип — `SharedReview` у `src/reviewsApi.ts`.

| Поле | Значення |
| --- | --- |
| `id` | Стабільний ідентифікатор. Для ручного запису створюється в браузері через `crypto.randomUUID()`. |
| `source` | Джерело відгуку. |
| `date` | Дата відгуку у форматі `YYYY-MM-DD`. |
| `url` | Посилання на оригінал, може бути порожнім. |
| `author` | Автор або нік; за відсутності — `Без імені`. |
| `rating` | Ціле число 1–5 або `null`. |
| `content` | Текст відгуку. |
| `reply` | Підготовлена/опублікована відповідь. Порожній рядок означає, що відповіді немає. |
| `internalNote` | Внутрішня нотатка, яку гість не бачить. |
| `assignee` | Необов’язковий відповідальний менеджер. |
| `status` | `new`, `needs_reply`, `draft`, `sent` або `closed`. |
| `respondedAt` | ISO-час відповіді або порожній рядок. |
| `createdAt`, `updatedAt` | Час створення та версія для захисту від конфліктів. |
| `images`, `video`, `tags` | Додаткові дані старих/імпортованих записів. |

Статуси:

- `new` — новий сигнал, ще не розібраний.
- `needs_reply` — потрібна відповідь або подальша дія.
- `draft` — відповідь готується.
- `sent` — відповідь опублікована менеджером у джерелі.
- `closed` — роботу завершено.

## Синхронізація та помилки

- Джерелом правди є тільки сервер. Постійний `localStorage`-кеш відгуків не використовується і не повинен повертатися.
- Список завантажується з `cache: no-store` та cache-busting параметром.
- Запити мають таймаут 45 секунд.
- Мутації виконуються послідовно; паралельна мутація блокується.
- Після `create`, `update` або `delete` UI одразу оновлює локальний результат і повторно читає весь список із сервера.
- Повільна стара відповідь списку не повинна перезаписувати новішу підтверджену мутацію.
- Якщо запис прийнятий сервером, але повторне читання не вдалося, інтерфейс не стверджує, що операція втрачена: просить оновити список перед повторною спробою.
- Якщо API недоступний, старі дані з минулої сесії не показуються як актуальні.

## Контракт Reviews API v2

### GET

- `?action=health` → `{ ok: true, version: 2, capabilities: ['delete', 'clearReply'], ... }`
- `?action=list` → `{ ok: true, reviews: [...], updatedAt: ... }`

### POST

Запити надсилаються як `text/plain;charset=utf-8` із JSON у body, щоб не створювати проблем із preflight для Apps Script.

- `{ action: 'create', review }` → повертає створений `review`; повтор із тим самим `id` ідемпотентний.
- `{ action: 'update', id, changes }` → повертає оновлений `review`; `updatedAt` використовується для виявлення конфлікту.
- `{ action: 'delete', id }` → фізично видаляє рядок і повертає `{ ok: true, deleted: true, id }`.
- `{ action: 'bulkUpsert', reviews }` → додає відсутні записи та не перезаписує менеджерські поля існуючих записів.

Сервер використовує `LockService`, `SpreadsheetApp.flush()` і точну перевірку заголовків аркуша. Старі рядки без `ID` знаходяться через fallback на `Review URL`.

## Доступ і безпека

Власник 2026-10-13 свідомо підтвердив відкритий модуль та відкритий Apps Script web app без окремого логіна. Це означає, що endpoint дозволяє публічні create/update/delete. Не додавайте клієнтський секрет у React: він не створить захисту. Якщо вимоги зміняться, потрібна серверна автентифікація або інший бекенд, а не прихований рядок у frontend bundle.

Google Sheet і Apps Script є технічним сховищем та бекендом. Менеджер працює тільки через CRM.


На Windows для UI-тесту можна вказати встановлений Edge або Chrome через `BROWSER_PATH`. Тест перевіряє desktop `1440px`, mobile `390px`, CRUD, очищення відповіді, підтвердження видалення, збереження даних при помилці, захист від старої відповіді, поведінку при падінні API та відсутність горизонтального overflow.

## Деплой

Frontend:

1. Працювати в окремій гілці та відкрити PR у `main`.
2. Дочекатися успішного workflow `Validate MARMOO BI v2`.
3. Після merge workflow `Deploy MARMOO BI to GitHub Pages` перевіряє Reviews API v2, збирає весь BI та force-pushить готовий `dist` у `gh-pages`.
4. Перевірити живу сторінку та `dist/build-info.txt`.

Backend:

1. Зміни у `google-apps-script/reviews-api.gs` не деплояться через GitHub.
2. Оновити код у відповідному Apps Script project.
3. Створити нову версію наявного web app deployment, зберігши той самий URL і погоджені налаштування доступу.
4. Перевірити `health`, потім повний CRUD на тимчасовому записі та видалити тестовий запис.
5. Лише після цього зливати frontend, який залежить від нового контракту.

Production workflow навмисно завершується помилкою, якщо Reviews API недоступний, повертає HTML, має версію не `2` або не оголошує capability `delete`.

## Правила для наступних змін

- Не змінюйте схему `REVIEW_HEADERS` без одночасної міграції аркуша, API, типів і тестів.
- Не робіть оптимістичний UI єдиним доказом збереження; потрібне серверне підтвердження та повторне читання.
- Не замінюйте фізичне видалення зміною статусу.
- Не повертайте persistent cache, який може маскувати падіння API.
- Не вважайте збережену відповідь автоматично опублікованою у зовнішньому джерелі.
- Не повертайте CSV-імпорт або фільтр за відповідальним у менеджерський UI без нового продуктового рішення.
- Не ламайте інші BI routes; запускайте TypeScript, production build і наявні smoke/UI тести.

## Відомі обмеження

- Немає автентифікації, ролей та аудиту дій.
- Видалення є остаточним; відновлення можливе лише з резервної копії Google Sheet.
- Apps Script може підтвердити запис уже після клієнтського таймауту. У такій ситуації спочатку оновіть список, а потім вирішуйте, чи повторювати дію.
- Відповіді у зовнішні сервіси не публікуються автоматично.
- `bulkUpsert` збережений у API для технічних сценаріїв, хоча кнопки імпорту в CRM немає.
- Основний frontend bundle має наявне попередження Vite про розмір; це не специфічна проблема Reviews CRM.
